# 06. Технологии хранения данных

---

## 1. Сущности и их атрибуты

| Сущность | Атрибуты | Описание |
|---|---|---|
| **Restaurant** | id, name, owner_user_id, cuisine_type, cuisine_confidence, created_at, updated_at | Профиль ресторана |
| **Menu** | id, restaurant_id, raw_text, dishes_json, uploaded_at, file_hash | Загруженное меню ресторана |
| **Dish** | id, menu_id, name, category, ingredients_hints[] | Блюдо из меню |
| **Product** | id, name, category, subcategory, description, images[], compatible_cuisines[], badges[], source_url, farmer_id, cached_at | Продукт из каталога svoe-rodnoe.ru (кэш) |
| **Season** | id, product_id, start_month, end_month, is_year_round | Сезонные окна продукта |
| **Farmer** | id, name, region, profile_url, cached_at | Фермер из svoe-rodnoe.ru (кэш) |
| **Recommendation** | id, restaurant_id, product_id, ai_explanation, menu_matches_json, generated_at, ttl | Сгенерированная рекомендация |
| **CuisineType** | id, name_ru, name_en, compatible_categories[] | Справочник типов кухонь |
| **UserSession** | id, user_id, restaurant_id, created_at, expires_at | Сессия пользователя |
| **ViewHistory** | id, restaurant_id, product_id, viewed_at | История просмотров продуктов |

## 2. Акторы и взаимодействия с данными

| Стейкхолдер | Действия с данными | Характер взаимодействия |
|---|---|---|
| **Шеф-повар** | Загрузка меню, просмотр тайм-лайна, фильтрация продуктов, чтение рекомендаций | OLTP: частые, точечные чтения и записи |
| **Система (AI-модуль)** | Генерация объяснений совместимости по запросу | OLTP: synchronous write on demand |
| **Система (каталог-синк)** | Периодическая синхронизация данных из svoe-rodnoe.ru (кэш) | Batch / Streaming: фоновое обновление каждые 24ч |
| **Система (аналитика)** | Агрегация: MAU, CTR, топ продуктов, рост транзакций (v2.0) | OLAP: агрегация за периоды (день/неделя/месяц) |
| **PM / Аналитик** | Просмотр дашбордов KPI | OLAP: чтение агрегированных отчётов |
| **Фермер (через svoe-rodnoe.ru)** | Обновление каталога и данных о сезонности | Не прямое: через sync job |

## 3. Матрица критериев выбора хранилища

| Критерий | Restaurant / Menu / Dish | Product / Season / Farmer (кэш) | Recommendation (AI) | ViewHistory (аналитика) | CuisineType (справочник) |
|---|---|---|---|---|---|
| **Объём данных** | Малый (тысячи ресторанов) | Средний (~100K продуктов) | Малый (ротация 24ч) | Большой (миллионы строк) | Очень малый (<100 строк) |
| **Паттерн записи** | Редкая запись (обновление меню) | Batch раз в 24ч | Запись при генерации | Append-only потоком | Только при обновлении справочника |
| **Паттерн чтения** | Точечное (по ID ресторана) | Частое, с фильтрами и сортировкой | Точечное (по restaurant+product) | Агрегированное | Полное (весь справочник за раз) |
| **Консистентность** | Strong (меню должно быть актуальным) | Eventual (кэш ≤24ч — допустимо) | Eventual | Eventual | Strong |
| **Доступность** | High (99%) | High (с fallback на кэш) | Degraded acceptable (AI может не отвечать) | Eventual | High |
| **Мутабельность** | Да (меню обновляется) | Перезапись при синк | Перезапись при TTL | Immutable (append only) | Редко |
| **Транзакции** | Нужны (загрузка меню = атомарная операция) | Не нужны | Не нужны | Не нужны | Не нужны |
| **Поиск** | По ID | Полнотекстовый + фильтры | По составному ключу | Аналитические запросы | Нет |
| **Стоимость** | Низкая | Средняя (Redis) | Низкая | Высокая при OLTP-БД | Минимальная |

## 4. Итоговое решение с обоснованием

| Сущность | Тип хранилища | Выбор | Обоснование |
|---|---|---|---|
| **Restaurant, Menu, Dish** | Реляционная БД | **PostgreSQL** | Транзакционные операции при загрузке меню, связанные данные (menu → dishes), нужны JOIN'ы. PostgreSQL — зрелое решение с хорошей поддержкой JSONB для `dishes_json`. |
| **Product, Season, Farmer** (кэш каталога) | Кэш в памяти + Реляционная БД | **Redis** (горячий кэш, TTL 24ч) + **PostgreSQL** (персистентный fallback) | Продукты читаются очень часто при каждом открытии дашборда. Redis обеспечивает отклик <1мс. PostgreSQL — резерв при рестарте Redis или истечении TTL. |
| **Recommendation** | Кэш + БД | **Redis** (TTL 1ч) + **PostgreSQL** | AI-генерация дорога по токенам. Кэшируем результат на 1 час. Если за час тот же шеф запросит ту же пару (продукт+кухня) — ответ из кэша. |
| **ViewHistory** | Колоночная аналитическая БД | **ClickHouse** | Append-only данные в больших объёмах, нужны агрегации (COUNT, GROUP BY дата/продукт). ClickHouse превосходит PostgreSQL в аналитических запросах на 10–100x. |
| **CuisineType** | In-memory (приложение) | **Захардкожен в конфиг YAML** | Справочник из <100 строк, меняется редко, нет смысла в отдельной БД. Загружается при старте приложения. |
| **UserSession** | Кэш | **Redis** | Сессии — типичный use case Redis: TTL 8ч, быстрый lookup по токену. |

### Почему не выбраны альтернативы

| Отвергнутый вариант | Причина отказа |
|---|---|
| MongoDB для всего | Отсутствие транзакций и JOIN'ов критично для Menu/Dish; избыточен для данного объёма |
| Elasticsearch для продуктов | Сложность операционного обслуживания для хакатона; PostgreSQL + pg_trgm достаточен для MVP |
| ClickHouse для всего | Не поддерживает UPDATE/DELETE (только append) — неприемлемо для Menu и Restaurant |
| SQLite | Не масштабируется для concurrent-нагрузки 500+ пользователей |
