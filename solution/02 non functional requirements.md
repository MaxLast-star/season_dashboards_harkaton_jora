# 02. Нефункциональные требования (NFR)

## Производительность

```
ID: NFR-PERF-001
Категория: Производительность
Приоритет: MUST HAVE
Требование: Время загрузки дашборда сезонности (первый рендер) ≤ 2 секунды при скорости соединения 10 Мбит/с
Обоснование: Шеф-повар работает в напряжённом ритме кухни. Медленный интерфейс ведёт к отказу от инструмента. Порог 2 сек — стандарт для веб-приложений B2B по исследованиям Google (>53% пользователей уходят при загрузке >3 сек).
```

```
ID: NFR-PERF-002
Категория: Производительность
Приоритет: MUST HAVE
Требование: Генерация AI-объяснения совместимости продукта с кухней ≤ 3 секунды на один продукт
Обоснование: Основная ценность продукта — быстрые релевантные объяснения. Задержка >5 сек воспринимается как «зависание» и снижает доверие к AI-функционалу.
```

```
ID: NFR-PERF-003
Категория: Производительность
Приоритет: SHOULD HAVE
Требование: Система должна выдерживать одновременную нагрузку ≥ 500 активных пользователей без деградации времени ответа более чем на 50%
Обоснование: При MAU 5000 шефов и рабочем окне 8–14 часов ожидаемый пик — ~300–500 одновременных сессий. Закладываем 20%-й запас.
```

## Надёжность

```
ID: NFR-REL-001
Категория: Надёжность
Приоритет: MUST HAVE
Требование: Доступность сервиса ≥ 99% в рабочие часы (08:00–22:00 по МСК), что соответствует ≤ 7.2 часа простоя в месяц
Обоснование: Рестораны работают с раннего утра до поздней ночи. Недоступность в часы пик планирования меню (утро, обед) критична для бизнеса шефа.
```

```
ID: NFR-REL-002
Категория: Надёжность
Приоритет: MUST HAVE
Требование: При недоступности API svoe-rodnoe.ru система должна автоматически переключаться на кэш (TTL 24 часа) и уведомлять пользователя о давности данных
Обоснование: Зависимость от внешнего API — ключевой риск R5. Кэш гарантирует работоспособность даже при сбоях партнёрского сервиса.
```

```
ID: NFR-REL-003
Категория: Надёжность
Приоритет: SHOULD HAVE
Требование: RTO (Recovery Time Objective) ≤ 30 минут, RPO (Recovery Point Objective) ≤ 1 час
Обоснование: При сбое восстановление в течение 30 минут минимизирует потери пользовательского доверия. Потеря данных за последний час допустима, т.к. контент каталога статичен.
```

## Безопасность

```
ID: NFR-SEC-001
Категория: Безопасность
Приоритет: MUST HAVE
Требование: Все данные передаются по HTTPS (TLS 1.2+). Хранение паролей — bcrypt с cost ≥ 12. API-ключи хранятся в environment variables, не в коде.
Обоснование: Пользователи передают данные меню ресторана — конфиденциальную бизнес-информацию. Несоблюдение базовой безопасности создаёт юридические и репутационные риски для РСХБ.
```

```
ID: NFR-SEC-002
Категория: Безопасность
Приоритет: MUST HAVE
Требование: Авторизация через существующую систему svoe-shef.ru (SSO / OAuth 2.0). Сессия истекает через 8 часов бездействия.
Обоснование: Единая авторизация исключает дублирование учётных записей и соответствует стандартам платформы РСХБ.
```

```
ID: NFR-SEC-003
Категория: Безопасность
Приоритет: SHOULD HAVE
Требование: Rate limiting на AI-запросы: не более 60 запросов в минуту на одного пользователя. При превышении — HTTP 429 с понятным сообщением.
Обоснование: Защита от злоупотреблений API LLM, которые тарифицируются по числу токенов. Без ограничений возможны несанкционированные расходы.
```

## Удобство использования (Usability)

```
ID: NFR-UX-001
Категория: Удобство использования
Приоритет: MUST HAVE
Требование: Новый пользователь должен достичь первого результата (увидеть подборку сезонных продуктов) за ≤ 5 шагов и ≤ 3 минуты без инструкции
Обоснование: Критерий оценки хакатона — «минимизация действий для поиска продуктов». Шеф-повара — практики, не технари; они не будут читать мануал.
```

```
ID: NFR-UX-002
Категория: Удобство использования
Приоритет: SHOULD HAVE
Требование: Интерфейс адаптирован для экранов от 1024px (десктоп). Мобильная версия — v2.0.
Обоснование: Шефы преимущественно работают с планшетом или ноутбуком на кухне / в офисе. Мобильная версия важна, но не является MVP-требованием.
```

```
ID: NFR-UX-003
Категория: Удобство использования
Приоритет: COULD HAVE
Требование: Интерфейс поддерживает тёмную тему (переключатель в настройках)
Обоснование: Кухни часто имеют специфическое освещение. Тёмная тема снижает нагрузку на глаза при длительной работе. Реализация опциональна для MVP.
```

## Поддерживаемость (Maintainability)

```
ID: NFR-MAINT-001
Категория: Поддерживаемость
Приоритет: SHOULD HAVE
Требование: Тестовое покрытие бизнес-логики (подбор продуктов, классификация кухни) ≥ 70% unit-тестами
Обоснование: Алгоритм подбора продуктов — ключевая ценность системы. Без тестов любое изменение рискует сломать основную функцию.
```

```
ID: NFR-MAINT-002
Категория: Поддерживаемость
Приоритет: SHOULD HAVE
Требование: База сезонности продуктов вынесена в отдельный конфигурационный файл (JSON/YAML), не закодирована в бизнес-логике. Обновление базы — без деплоя.
Обоснование: Сезонные окна меняются год от года и требуют регулярной корректировки. Жёсткое кодирование сделает обновления дорогостоящими.
```

## Совместимость

```
ID: NFR-COMPAT-001
Категория: Совместимость
Приоритет: MUST HAVE
Требование: Сервис работает в браузерах: Chrome ≥ 90, Firefox ≥ 88, Safari ≥ 14, Edge ≥ 90. Без дополнительных плагинов.
Обоснование: Целевая аудитория использует разные устройства. Ограничение браузерами последних 2 лет охватывает >95% реальных пользователей.
```

```
ID: NFR-COMPAT-002
Категория: Совместимость
Приоритет: MUST HAVE
Требование: API для интеграции с svoe-rodnoe.ru использует REST + JSON. При изменении схемы API — обратная совместимость поддерживается минимум 3 месяца.
Обоснование: Изменения на стороне svoe-rodnoe.ru не должны моментально ломать работу дашборда. Трёхмесячный буфер позволяет провести плановую миграцию.
```

## Почему другие категории не включены в MVP

| Категория | Причина исключения | План |
|---|---|---|
| **Масштабируемость** | Хакатонный прототип; реальная нагрузка неизвестна | v2.0: горизонтальное масштабирование, CDN |
| **Локализация** | Только русский рынок и русский язык | v3.0: мультиязычность при выходе на СНГ |
| **Доступность (a11y)** | Целевая аудитория — профессионалы без особых потребностей | v2.0: WCAG 2.1 AA |
| **Аудит и логирование** | Прототип не требует полного audit trail | v2.0: централизованное логирование (ELK) |
| **GDPR/152-ФЗ (полный)** | Базовые требования покрыты NFR-SEC; полный комплаенс — в продакшн версии | До продакшн запуска |
